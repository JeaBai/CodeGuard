# ADR-000 · <决策标题>

> **ADR（Architecture Decision Record）** 记录「架构上重要的决策」及其**理由与后果**。
> 规则（来自原始定义）：
> - 一页或两页为宜，**当作写给未来的开发者的一封信**
> - 编号单调递增、**不复用**；被推翻的标 `superseded` 而**不删除**
> - **所有后果都要列出，不只是好的那些**
>
> **为什么值得写**：不记录理由时，新人只有两条路——**盲目接受** 或 **盲目修改**。
> 项目积累太多「未经理解就被接受」的决策后，团队会害怕改动任何东西。

## 示例（已填写的参考样式）

**ADR-001 · 采用 SITL 而非仅依赖真飞来验证控制律**

- 状态：已接受　日期：2026-09-11　决策人：`<name>`

**背景**：一轮硬件迭代（改原理图→打板→贴片→调试）的现实反馈周期是 3–7 天，长则 3–4 周；真飞成本高且炸机风险大。而控制律（姿态解算、PID）的逻辑正确性无需硬件即可验证。

**决策**：**我们将**把零硬件依赖的纯逻辑模块（姿态解算、滤波器、PID）抽到 host 侧，用单元测试 + SITL 做高频回归；HIL 与真飞只用于验证时序、外设与整机行为。

**备选方案**

| 方案 | 优点 | 缺点 | 为何未采纳 |
|---|---|---|---|
| 只靠真飞验证 | 最真实 | 反馈周期 3–7 天、炸机成本高、样本量小 | 迭代速度不可接受 |
| 只靠纯仿真 | 秒级反馈 | 无法暴露外设与时序问题 | 覆盖不全 |
| **分层验证（SITL + HIL + 真飞）**（采纳） | 反馈快 + 覆盖全 | 需额外搭建 host 测试环境 | — |

**后果**

- 正面：单元测试约 30 秒一轮，相对 3–7 天的硬件迭代是数量级改善
- 负面：需要前期投入搭建 host 侧构建与打桩（约 3–5 人日）
- 风险：**SITL 通过不代表真机通过**——时序与外设仍需 HIL/真飞覆盖，不能因此减少真飞验证项
- 跟进：☐ 抽取纯逻辑模块　☐ 接入 Unity/CMock　☐ 建立 SITL 通路
