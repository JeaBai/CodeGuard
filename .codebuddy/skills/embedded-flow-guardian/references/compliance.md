# 合规标准强制产物矩阵

> 本文件回答：**如果项目要面向车规/工业/医疗/航空客户，必须先补齐哪些管理性产物。**
> 标注 `[A]` 标准组织/官方 · `[B]` 专业机构 · `[C]` 咨询/市场报告（需交叉验证）。完整来源见 `sources.md`。

## 1. 五大标准对照

| 标准 | 分级 | 强制管理性产物 | 独立性要求 | 工具资质 |
|---|---|---|---|---|
| **ISO 26262** | ASIL A–D（HARA 由 S/E/C 判定） | 安全计划、**DIA（开发接口协议）**、FSC/TSC、双向追溯、变更管理、Safety Case | Part 2 三类确认措施；**ASIL D 要求组织外部独立** | Part 8 Cl.11：TI1/TI2 × TD1–TD4 → **TCL1/2/3** |
| **IEC 61508** | SIL 1–4 | FSM（安全管理）、安全计划、SRS、配置与变更管理、全生命周期追溯、HAZOP/FMEA | **SIL3/4 需第三方独立认证/评估** | 要求「经过验证的工具」与编码规范 |
| **DO-178C** | DAL A–E | **PSAC** + 开发/验证/配置管理/质量保证四类计划、双向追溯矩阵、生命周期数据 | 高 DAL 目标须「带独立性」满足（评审者≠作者） | **DO-330 工具资质** |
| **IEC 62304** | Class A/B/C | 开发计划、需求、架构（B/C）、详细设计（C）、单元验证（B/C）、集成与系统测试、配置管理、问题解决、风险管理 | 无强制外部独立性 | 未强制资质，但要求 **SOUP 评估** |
| **ASPICE 4.0** | CL0–CL5（基于 ISO/IEC 33020:2019） | 组织级标准过程 + 裁剪规则、双向追溯、配置管理、变更/问题管理、验证证据 | 由 intacs 认证评估师评估 | — |

**四份强制交集产物**：安全/开发计划、**双向追溯矩阵**、配置管理计划、验证计划。差异只在「独立性等级」「覆盖率深度」「工具资质要求」。

## 2. ASPICE 4.0 关键事实

**官方状态** `[A]`

- 由德国汽车工业协会 **VDA QMC** 维护，**2023-11-29 正式发布**
- **本质是过程评估模型，不是认证**
- **11 个过程组、32 个过程**（UL Solutions 按生命周期归类统计为 8 个过程组，两种口径都成立，取决于分组方式）

**结构变化（4.0 vs 3.1）** `[A]`

| 变化 | 内容 |
|---|---|
| **新增 3 个过程组** | **HWE**（硬件工程 HWE.1–4）、**MLE**（机器学习工程 MLE.1–4 + SUP.11）、**VAL**（验证 VAL.1） |
| **删除 10 个过程** | ACQ.3、ACQ.11–ACQ.15、SPL.1（很少使用）、SUP.2（与 SUP.1 重复）、SUP.4、SUP.7（与 SUP.8 重复） |
| **术语变更** | 把「测试」全面改写为「**验证（Verification）**」 |
| **规模** | VDA Scope 基本实践数从 265 降到 **199** |

**VDA Scope 构成**：`BASIC + 至少一个工程过程组`，工程过程组按产品类型选：
- 系统开发 = BASIC + SYS
- 电子开发 = BASIC + SYS + **HWE**
- 纯软件 = BASIC + SWE

**中国市场实际要求** `[B]`

- 多数 OEM 要求 Tier1 达 **CL2** 及以上
- VW、BMW 等对部分项目要求 **CL3**；安全相关项目建议 CL3
- 周期（咨询机构经验值）：从零起步达 CL2 约 **6–8 个月**，达 CL3 约 **12–18 个月**
- 证书**有效期 3 年**，第 1/2 年监督审核，第 3 年再认证

> ⚠️ **费用数据**（`[C]` 市场报告，仅作量级参考）：入门级 CL2 聚焦评估约 3.5 万–6 万美元；完整范围 3.5 万–15 万美元；CL4–5 含咨询 10 万–20 万美元。

## 3. ISO 26262 关键细节

**DIA（开发接口协议，Part 8 Cl.5）必含内容** `[A]`

- 双方 FS-Manager
- **RASIC 责任矩阵**
- 分配到供应商的安全需求及其 ASIL
- ASIL 分解的独立性假设
- 接口与时序（FTTI / FDTI）
- **交付物清单**
- 沟通与异常上报（含 SOP 后现场故障上报）
- 变更管控（**区分普通变更 vs 安全变更**）
- FSA 协调与证据访问权

**工具资质机制（Part 8 Cl.11）** `[A]`

```
TI1（不可能引入/漏检错误） / TI2（其他）
        ×
TD1（高置信检出） … TD4（未知）
        ↓
TCL1（无需资质） / TCL2 / TCL3（必须资质）
```

- **四种资质方法**：1a 使用经验置信、1b 评估工具开发过程、1c 工具验证、1d 按安全标准开发
- ASIL D 首选 **1c / 1d**
- ⚠️ **常见误解：「TCL2 比 TCL1 更好」是错的**——TCL 是分类结果，不是等级高低

**确认措施与独立性**

| 确认措施 | ASIL A | ASIL B | ASIL C | ASIL D |
|---|---|---|---|---|
| Confirmation Review | I0/I1 | I1 | I2 | I2 |
| Safety Audit | 不需要 | I0（可选） | I2 | I2 |
| Safety Assessment | — | I1（建议） | I2 | **I2/I3** |

> ⚠️ 不同来源对独立性等级编号不一致（一套标 I0–I3，另一套标 I1–I4）。
> **实操读法**：等级越高，要求越「外部化」——ASIL C/D 要求跨团队/跨部门，ASIL D 的评估最好由**第三方（TÜV/SGS/DNV/exida）**执行。

## 4. DO-178C

**目标数与覆盖率** `[A]`（已多源核实）

| DAL | 失效条件 | 目标数 | 结构覆盖率 |
|---|---|---|---|
| A | Catastrophic | **71** | 语句 + 判定 + **MC/DC** |
| B | Hazardous | **69** | 语句 + 判定 |
| C | Major | **62** | 仅语句 |
| D | Minor | **26** | 无 |
| E | No Safety Effect | 0 | 无 |

> ⚠️ 各来源对「需独立完成的目标数」口径不一（有 30/18/5/2、33/21/8/5、31/19/5/2 等多组数据）。**引用时须注明所依据的标准版本与来源，不要直接套用单一数字。**

**其它要点**
- **DO-178C 与 ISO 26262 无规范级互认**：DAL 与 ASIL 之间**没有 normative cross-walk**
- 四份补充文件：DO-330（工具资质）、DO-331（模型开发）、DO-332（面向对象）、DO-333（形式化方法）
- 六个过程组：规划、开发、验证、配置管理、质量保证、适航联络

## 5. IEC 62304（医疗软件）

- 分类依据是「失效可能造成的**最严重伤害**」，且**假设软件失效概率为 100%**
- 软件内部的防护措施**不能**降低等级，只有**软件之外的独立风险控制**（硬件联锁、独立报警）可以
- **产物阶梯**：
  - **A**：开发计划、需求、单元实现、系统测试、发布
  - **B 追加**：架构设计、单元验证、集成测试、**需求→测试全量追溯**
  - **C 追加**：详细设计
- **SOUP（不明来源软件）必须识别、规定其要求并管理缺陷**；**SBOM 不等于 SOUP 合规**

## 6. 覆盖率等级要求

| 覆盖率 | ASIL A | ASIL B | ASIL C | ASIL D |
|---|---|---|---|---|
| 语句覆盖 | ++ | ++ | + | + |
| 分支覆盖 | + | ++ | ++ | ++ |
| MC/DC | + | + | ++ | ++ |

（++=高度推荐、+=推荐）

> **重要辨析**：ISO 26262 **没有「强制」档**，覆盖率表是「推荐/高度推荐」，且属**可替代条目（alternative entries）**，项目须论证所选组合——这与 DO-178C DAL A 的 MC/DC **强制**要求有本质区别。

## 7. 编码规范与合规率

**MISRA 版本谱系** `[A]`（已核实）

| 版本 | 年份 | 规模 | 关键变化 |
|---|---|---|---|
| MISRA-C:1998 | 1998 | 127 条 | 起点（C90） |
| MISRA-C:2004 | 2004 | 141/142 条 | 首次分级（Required/Advisory） |
| MISRA C:2012 | 2012 | 143 规则 + 16 指令 = 159 | 引入三级分类、rule/directive 分离 |
| C:2012 AMD1–AMD4 | 2016–2023 | 逐步累加 | 安全规则（源自 CERT C）、C11 核心、C11/C18 特性、多线程与原子 |
| **MISRA C:2023** | 2023 | **221 条** | 合并全部 AMD + TC 为单一文档 |
| **MISRA C:2025** | 2025-03 | **225 条** | 新增 5 条；首次引入「已删除/已停用」概念；Rule 15.5（单一出口）被 disapplied；**明确 AI 生成代码与人工代码同标准** |

**三级分类的合规含义**

| 分类 | 含义 |
|---|---|
| **Mandatory** | 必须遵守，**不允许任何偏离**（数量很少） |
| **Required** | 原则上必须遵守，**可经正式偏离流程批准后例外** |
| **Advisory** | 良好实践，可按项目裁量；**可被升级为 Required，不可反向降级** |

**偏离（Deviation）流程的正式产物**（MISRA Compliance:2020）

| 产物 | 含义 |
|---|---|
| **GEP**（Guideline Enforcement Plan） | 逐条记录每条准则的强制方式（工具/人工评审） |
| **GRP**（Guideline Recategorization Plan） | 记录类别调整（如 Advisory→Required）的正式决定 |
| **Deviation Records** | 每条经批准的例外，含准则号、适用场景、正当性、风险对比、安全论证 |
| **GCS**（Guideline Compliance Summary） | 项目收尾时逐条声明合规等级 |
| **Permits** | 预先批准的高频偏离模式，避免重复论证 |

合规等级只有四档：**Compliant / Deviations / Violations / Disapplied**；且 **Mandatory 只能声明 Compliant**。

**C++ 侧已收敛**：**MISRA C++:2023（2023-10，面向 C++17，179 条）整体吸收并取代 AUTOSAR C++14**；AUTOSAR 已正式退役独立 C++14 指南并改为引用 MISRA C++:2023。

**合规率实测**（IEEE 2023，最可靠的一项公开实证）`[A]`

- 样本：**16 个 RTOS，共 1,451,472 行代码**
- 违规行 100,143 行 = **6.90%**
- 按类别：Mandatory **444 处（0.03%）**、Advisory 43,570 处（3.00%）、Required 56,129 处（3.87%）
- 项目间差异巨大：**LiteOS 20.00%、phoenix 18.89%、Mbed 12.99%** vs **RTEMS 2.05%、QP/C 2.74%**
- 14/16 个 RTOS 对被测 Mandatory 规则**零违规**

> ⚠️ **重要辨别**：Les Hatton 2003 年测得 MISRA C 平均违规率约 **600 处/1000 行可执行代码**，信噪比仅 **0.01–0.1**。
> 这意味着**「合规率高」未必等于「缺陷少」**——工具噪声与规则冗余是长期问题。

**LLM 生成代码的 MISRA 基线**（2025–2026，26 个 C++ 任务 × 20 次运行）
- 各模型基线违规率 23.64–29.28 次/KLOC
- 最常违反集中于 Advisory（标准整型名、运算符优先级加括号）与 Required（数值类型赋值、循环/条件复合语句）
- **加入 Top-5/Top-10 规则提示后违规最高降幅 83%**

## 8. 标准对编码规范的强制力

| 标准 | 要求 | 强度 |
|---|---|---|
| **ISO 26262** Part 6 | 按 ASIL 推荐「应用编码准则/语言子集」 | 行业事实强制 |
| **IEC 61508** Part 3 | 编码标准「降低错误可能性」**所有 SIL 均为 HR**；语言子集 **SIL3–4 为 HR**；防御性编程 SIL3–4 为 HR | HR（不采用必须提交并获批的书面理由） |
| **DO-178C** | 编码标准是预期产物，但不点名 MISRA | 目标级要求 |
| **EN 50128**（铁路） | 低 SIL 推荐、**高 SIL 强制** | 强制（高 SIL） |

> **注意**：MISRA 不点名、IEC 61508 也不点名，但两者都要求「语言子集 + 编码标准」。MISRA 是行业事实标准；**法律强制力来自合同与功能安全标准，而非 MISRA 本身**。

## 9. 组织与独立性（决定人员编制）

**唯一硬边界是「独立性」**

- **ASIL A**：确认审查允许 I0（同项目自行评估可接受）→ 小团队可高度兼岗
- **ASIL B**：审查需 I1（作者之外的另一个人，可同团队）→ **3–5 人团队可满足**
- **ASIL C**：全部三类确认措施需 I2（独立团队，不同直属经理）
- **ASIL D**：评估需 I2/I3（跨部门或外部第三方）→ **小团队无法内部满足，必须外购评估**

**兼岗实践建议**
1. 角色与人员**解耦**——一人可任多角色，但「是否可兼」由独立性矩阵决定，不由人数决定
2. 小团队把**功能安全经理 + 配置管理**合并常见且合规，但**「作者」与「确认审查者」不能是同一人**
3. ASIL D 项目按模块拆分子项，把最高独立性要求**下沉到最危险的安全目标**上
4. 用 intacs Competent Assessor / TÜV FSEng 认证作为**外部独立资源池**的采购凭证

**认证价格参考** `[B]`

| 认证 | 路径 | 价格 |
|---|---|---|
| **intacs 认证** | Process Expert → Provisional Assessor → Competent Assessor | Provisional Assessor 公开课 **€2,000/人 + €450 考试费**；内训 **€10,000/12 人**；Competent Assessor 公开课 **€2,750/人 + €550 考试费** |
| **FS Engineer (TÜV Rheinland)** | ≥3 年功能安全经验 + 工程学位 + 完整课程 + 考试；**证书有效期 5 年** | 机械安全在线课 **$2,700/人**；Risktec 机械方向 **£2,300**（考试单独 £700） |

## 10. 落地建议：什么时候**不**上合规体系

**ASPICE 不必作为个人/小团队项目的目标**——它的价值在「对客户的准入证明」。个人自研项目无客户审计压力，强行上 ASPICE 的直接后果是**3–5 倍工作量**（从业者经验值）。

**但如果未来接车企/工业客户，L2 是硬门槛。**

**本土落地的三个教训**（`[B]` 从业者复盘）

- 某供应商被要求「必须用 SVN 锁定文档打基线」，结果基线工具与需求工具数据割裂，「打完基线之后，大家还是看着不断变化的需求做开发，**基线失去了意义**」
- 「有一次我们为了证明『需求评审确实召开过』，不得不让项目经理在周末召集全员开**补录会议**」
- 「横向裁剪」埋雷：只在有客户评审要求的项目上走 ASPICE，导致「当某个『简易项目』突然被客户要求审计时，团队因不熟悉 DOORS，**被迫返工 3 个月**」

> **反直觉案例**：某团队 TBOX 项目 3 个多月交付后「质量出奇的好……总 BUG 就是个位数」，但**拿去评 ASPICE 没有通过**，被提了一堆问题。
>
> **判断**：国内 ASPICE 的痛点**不在标准本身，而在「评估导向」的执行方式**。支持派的关键论证是「**准入门槛**」而非「质量提升」；反对派的关键论证是「**性价比极低**」。
