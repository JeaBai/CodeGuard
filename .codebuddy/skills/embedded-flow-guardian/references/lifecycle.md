# 生命周期与交付物

> 本文件回答两个问题：**研发分几个阶段、每个阶段的产物是什么、准出准则是什么**。
> 数据来源与可信度见 `sources.md`。凡标注「经验性判断」处，均为跨来源比对推断而非直接引用。

## 1. 五种生命周期范式（先选对的，再看是否叠加）

| 范式 | 阶段划分 | 优化目标 |
|---|---|---|
| **嵌入式 V 模型** | 需求 → 规格 → 系统架构 → 硬件/软件设计 → 实现 → 各自测试 → 系统集成 → 系统确认 → 运维 | 正确性 |
| **IEC 61508 安全生命周期** | **16 阶段**：概念 → 范围定义 → 危险与风险分析 → 整体安全要求 → 安全要求分配 → 运维/验证/安装规划 → 实现 → 安装与试运行 → 整体安全确认 → 运行维护 → 修改改造 → 退役处置 | 功能安全（SIL 1–4） |
| **ISO 26262 安全生命周期** | 概念（Item 定义、HARA、安全目标）→ 产品开发（系统/硬件/软件）→ 生产与运行 | 汽车功能安全（ASIL A–D） |
| **NPI 新产品导入** | 策划 → **EVT**（工程验证）→ **DVT**（设计验证）→ **PVT**（生产验证）→ **MP**（量产），每阶段设 Gate Review | 可制造性 |
| **IPD 集成产品开发** | 概念 → 计划 → 开发 → 验证 → 发布 → 生命周期管理；DCP + TR 双轨评审 | 商业回报 |

**关键辨析**

- **V 模型的本质是「对称性」**：左侧每个阶段的输出，就是右侧对应层级验证的输入。
- **安全生命周期 ≠ 开发流程**：IEC 61508 的生命周期只承载「安全活动」，与功能开发流程**并行运行**；且明确包含开发完成后的安装、确认、运维、改造、退役五个阶段。
- **NPI 的 EVT/DVT/PVT 边界在业界并不统一**（经验性判断）——引用时须注明定义来源。

**选型原则**：先问「我优化的是正确性、安全性、可制造性还是商业回报」，再看该范式是否覆盖对应阶段。**安全项目必须额外叠加安全生命周期，不可用 NPI 或 IPD 替代。**

## 2. 十阶段：活动 / 输入 / 输出 / 准出

| # | 阶段 | 核心活动 | 主要输出（交付物） | 准出准则 |
|---|---|---|---|---|
| 1 | 需求与概念 | 明确用户/场景/危害/误用/环境/寿命/产量假设；系统边界 | 产品需求规格书（含可测性、时序、功耗、寿命、安全、合规）、可行性报告、**证据计划** | 每条需求可测量、有唯一 ID、有验收判据 |
| 2 | 系统/架构设计 | 软硬件划分、接口、数据流、时序与内存预算、电源状态、信任边界、诊断与升级策略 | 系统架构文档、软/硬件架构规格、**ICD**、内存映射、中断与时序预算、电源状态机 | 接口全部冻结并写入 ICD；内存/时序有预算表 |
| 3 | 详细设计 | 状态机、任务优先级、缓冲、持久化、驱动契约、错误处理、算法、测试接缝 | 模块规格、状态机图、驱动接口定义、单元测试计划 | 每个模块有可测接口；测试接缝明确 |
| 4 | 硬件设计 | 原理图、PCB 布局布线、层叠与阻抗、DFM/DRC | 原理图、**BOM**、**Gerber/钻孔**、层叠图、DFM 报告 | DRC/DFM 通过；BOM 有替代料 |
| 5 | 固件实现 | 编码规范、评审、静态分析、单元测试、小步集成 | **固件二进制**、单元测试报告、静态分析报告、评审记录 | 新增 BLOCK = 0；编码规范（MISRA 等）合规或已记录偏离 |
| 6 | 集成 | 按序点亮启动/时钟/存储器/外设/RTOS/中间件/应用 | 集成测试报告、**硬件-软件兼容矩阵** | 兼容矩阵覆盖所有板卡 Rev × 固件版本 |
| 7 | 验证与确认 | 需求验证、接口验证、可靠性/性能/安全验证；代表性条件下确认整机可用 | **测试报告**、覆盖率报告（如 MC/DC）、**RTM**、问题清单、安全评估与审计报告 | 需求关联覆盖率达标；RTM 双向无断链 |
| 8 | 试产/量产转移 | 冻结受控输入、复现构建、审批已知问题、产线测试、密钥注入 | 量产放行、产线测试规范、生产一致性计划、EVT/DVT/PVT 报告 | 同一 commit 可复现构建；已知问题已书面接受 |
| 9 | 现场维护 | 健康监控、事件分诊、漏洞与依赖管理、可恢复升级、变体支持 | OTA 包、变更记录、缺陷趋势报告 | 具备回滚能力；**回滚 ≠ 防降级** |
| 10 | EOL/退役 | 停产规划、长期器件供应评估、退役处置 | 退役处置记录、EOL 通告 | 器件生命周期风险已评估 |

## 3. 三份最高杠杆产物

| 产物 | 为什么高杠杆 | 缺失后果 |
|---|---|---|
| **需求规格书** | 需求波动会级联传导至设计、代码、测试、风险工件 | 下游全部返工，且返工成本随阶段指数上升 |
| **ICD（接口控制文档）** | 硬件与固件团队之间的「合同」，规定寄存器映射、内存地址、时序要求 | 硬软件各自「猜」接口，集成期才发现不匹配 |
| **RTM（需求追溯矩阵）** | 认证必查项；是「变更影响分析」和「覆盖充分性证明」的唯一载体 | 每次需求变更静默失效多条链接，验证退化成「取证调查」 |

> **行业原则**：**证据应随设计生长，而不是在发布前重建**（evidence should grow with the design, not be reconstructed at release）。

**可引用的反面案例（Mars Climate Orbiter，$3.276 亿）**

- 根因：地面软件用**英制单位（lbf·s）**输出，而软件接口规范**明确规定用公制 N·s**。误差因子 **4.45**。
- 后果：轨道估计偏差累积，最终在距火星地表约 **57 km** 处解体。
- **最扎心的细节**：至少两名导航员早就注意到偏差，但担忧被驳回，理由是「没有按规定填表记录他们的疑虑」。**制度化沟通渠道失效，比技术错误更致命。**

## 4. 硬软件并行：关键是「接口冻结」

| 机制 | 做法 |
|---|---|
| **接口冻结 + ICD** | 用硬件-软件接口（HSI）定义两侧交互；ICD 作为「合同」 |
| **HAL / BSP 抽象层** | HAL 暴露稳定 API，应用层不直接碰寄存器；换 MCU/换板只替换 BSP。三种模式：薄封装 / 分层 shim / 虚拟化 |
| **开发板先行** | 自研板未回板前用厂商评估板打通应用层，回板后只平移 BSP |
| **版本绑定矩阵** | 维护 板卡 Rev × 固件版本 × bootloader × 标定 的对应表 |
| **变更影响分析** | 供应链换料导致硬件变更时，需精确定位 HAL 中受影响的行 |

> **危险场景**：缺少兼容矩阵时，**面向 Rev B 准备的 OTA 包可能被错发到 Rev A 设备**。

## 5. 验证阶梯：MIL → SIL → SITL → HIL

| 级别 | 含义 | 需要硬件 | 典型实现 |
|---|---|---|---|
| MIL（模型在环） | 算法在模型中验证 | 否 | Simulink |
| SIL（软件在环） | 固件在 PC 上编译运行，传感器数据来自模型 | **否** | 普通 C++ 编译器编成本地可执行文件，可访问桌面全套工具 |
| SITL（软件在环+动力学） | 固件在 PC 运行 + 飞行动力学模型 | 否 | ArduPilot SITL |
| HIL/HITL（硬件在环） | **真实固件运行在真实硬件上**，仿真器注入传感器数据 | 是 | PX4 HITL |
| Simulation on Hardware | 硬件自身同时跑固件与仿真 | 是 | 可验证任务结构、舵面动作、失效保护，且不冒真机风险 |

**实践建议**：把「HAL 接口 + ICD」作为第一份冻结文档，在**架构阶段**就规划 SIL/HIL 双通路。

## 6. 七个最容易失控的环节

| 痛点 | 根因 | 缓解措施 |
|---|---|---|
| ① 需求变更失控 | 需求波动级联传导；变更未经统一影响分析就写基线 | 正式变更控制 + CCB；变更前强制影响分析；需求分级排序以支持优雅降级 |
| ② 追溯断裂 | 每次需求变更使多条链接静默失效 | 双向追溯贯穿生命周期；**手工矩阵第一次变更后即失效**，应上工具 |
| ③ 配置管理范围过窄 | 只管理源码，需求/设计文档游离在 SCM 之外 | 文档变更纳入同一变更管理；追溯链接与**具体版本/配置**绑定 |
| ④ 测试与集成滞后 | V 模型固有弱点即「集成晚」 | 左移：测试计划与设计阶段并行编写；单元测试先行 + CI |
| ⑤ 硬件返工 | 设计变更在 EVT 后成本指数上升；单一来源器件缺替代料 | EVT 前完成尽量多的预合规验证；为单一来源件定义替代料；长交期件提前采购 |
| ⑥ 器件停产与变体管理 | 维护期长于开发期（18 个月设计 → 可能 15 年在场） | 设计阶段即规划 OTA 基础设施、回滚安全与长期器件供应 |
| ⑦ 一线验证资源冲突 | HIL/仿真资源与硬件团队共享，无法每日自动测试 | 分层测试：算法 host 侧 mock；仿真层承担高频回归；HIL 只做时序/外设/整机 |

## 7. 反模式：让需求「假装被管理」

来自航天硬件从业者的公开复盘（《Uncontrolled Hardware Agile》）描述的失控路径：

- 需求永远不收敛，用户故事不断增殖，最后**故事悄悄变成事实上的需求**，没有真正的基线。
- 配置管理崩溃：接口漂移、修订分叉，最后**没人能回答「我们现在要出货/要做认证的是哪个配置？」**
- 失败模式是复利式的：**基线消失 → 返工爆炸 → 排期崩塌 → 成本螺旋**。

原文结论：*"Uncontrolled Hardware Agile does not fail because Agile is bad. It fails because **physics, manufacturing, and certification do not sprint**."*

**硬件需求冻结的可执行清单**：

- 客户需求书 / 技术规格书**双方签字**，且必须包含**可测量的验收标准**
- **需求追溯矩阵**：每个需求映射到设计项、测试与验收标准
- **变更必须走 CR / ECO**：描述、业务价值、工作量估算、对进度与成本的影响、责任人，缺一不可；**没有 CR 批准就不开工**
- **CCB 每周开会**，小额 PMO 批、大额高管签字
- **硬件 BOM 冻结**：量产前冻结物料清单，任何 ECO 需签字并给出返工成本
