# 反模式清单（做 / 不做对照）

> 本文件是可直接用于**评审对照**的检查表：左列是有证据支持的做法，右列是已被证伪或已产生实际事故的做法。
> 标注 `[A]`/`[B]`/`[C]`，完整来源见 `sources.md`。
> **用法**：评审/复盘时逐行扫描，命中右列即为风险项；写作时可直接引用作为论据。

## 1. 流程与需求

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 需求冻结日 + 阶段门 + CCB + **可测量的验收标准** + 追溯矩阵 | 让 scrum story 事实上承担硬件需求基线（硬件变更是**不可逆的物理代价**） |
| 变更前强制影响分析（工作量/进度/成本/冲突/设计·硬件·代码·测试） | 变更未经影响分析就写入基线 |
| 双向追溯贯穿 需求↔设计↔代码↔测试↔缺陷 | 用**手工矩阵**长期维护（**首次需求变更后即失效**） |
| 文档变更纳入同一变更管理，追溯链接绑定**具体版本/配置** | 只管理源码，需求/设计文档游离在 SCM 之外 |
| 用**参考类分布**汇报（「这类项目 18% 会超支 400%+」） | 用点估计承诺工期；引用「70% 项目失败」 |
| 测试计划与对应设计阶段**并行编写**（左移） | 把集成与测试留到最后 |
| 为单一来源器件定义替代料；长交期件提前采购 | EVT 之后才做 EMC/预合规验证 |

## 2. 协作与组织

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 设专职「胶水」工程师（single point of contact） | 靠加会议解决跨职能摩擦 |
| 把追溯做成工程对象，影响分析「在关系图上看范围」 | 把 bus factor = 1 当**文档问题**（应作为**架构缺陷**消除） |
| 管理是**可逆的职业变更**（6 个月试用）+ 双轨薪酬对等 | 「最资深工程师该当 tech lead」；因薪酬拓扑逼工程师转管理 |
| 管理者 6–8 名直接下属；**move scope, not people** | 把有限资源**平均撒**给所有团队（peanut buttering） |
| 反馈用 Observation → Impact → Question 三段式 | 用「is there anything I can improve」这种泛问 |
| 为 mentor 制度预留预算（**10 h/周·老工程师**、新人前 6 个月 30% 效能） | 让 mentor 制度变成自愿加班 |

## 3. 度量

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 指标**成组使用、互为约束**（吞吐与稳定性同时看） | 优化单一指标（牺牲评审与测试换低 lead time） |
| **比率**优于绝对值；加入同伴信号 | 用 LOC / 提交次数 / 缺陷关闭数考核 |
| **只用团队/组织级**；DORA 官方明确禁止用于个人绩效 | 用 DORA 指标跨团队横比（Web 团队 vs **嵌入式团队**） |
| 增量指标：新代码覆盖率 ≥80%、新代码重复率 ≤3%、新增 Blocker = 0 | 只看**全仓库绝对覆盖率**（在历史代码上永久卡住流水线） |
| 度量与**具体动作绑定**（超阈值即触发 CCB 或重新基线） | 度量只看不管，指标无治理意义 |

## 4. 版本控制与提交

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 持续交付用 TBD：≤3 活跃分支、每日合并、短分支 | 对持续交付**硬套 git-flow**（连作者都不推荐） |
| **固件用 `hardware/vx.x` 分支 + 量产 tag**（多版本在野是 git-flow 的正当场景） | 对需长期维护多版本的固件**硬套 TBD** |
| 大二进制走 Git LFS（含 `.gitattributes` 分类），CI 先 `git lfs install` | 二进制裸塞仓库；靠文件名 `Firmware_v2.3_final_FINAL_johns_fix.zip` 管理 |
| Atomic commit；Conventional Commits；写 **why** | 用「and」描述的巨型提交；`fix` / `WIP` / `final_final` |
| 每个出厂固件唯一对应一组源码版本（tag + 校验和） | 版本号写死在 `version.h`（不可追溯、易人为出错） |

## 5. 评审

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 单次 <200–400 行；<300–500 行/小时；60–90 分钟 | 一次审 2000 行；400 行 2 分钟秒批 |
| 多数变更**单人**评审（Google ~75%）；快反馈（小时内） | 教条要求所有变更两人批准 |
| 评审聚焦「为什么」；**风格交给自动化** | 以「缺陷数」考核评审者（实际仅 14% 评论与缺陷相关） |
| 明确「批准 = 我能共同负责」 | LGTM 秒批；为证明看了而挑格式 nitpick |

## 6. CI 与测试

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 门禁只拦**快且确定**的信号（编译、单测、lint、依赖扫描） | 「门禁一切」→ 红=噪声 → **门禁沦为剧场** |
| 慢/易抖的 HIL 与 soak 移到定时流水线 | 把 HIL 放在阻塞合并的路径上 |
| Flaky 用**自动隔离 + 开单 + 限时修复/删除** | 标记「连续 3 次失败才报警」（**会鼓励开发者忽视 flakiness**） |
| 构建时间控制在 **10 分钟**内 | 40 分钟流水线（催生「投机式推送」与浅评审） |
| 把 Jenkins 当**需预算供养的自有基础设施** | 「Jenkins 盒子应该自己一直跑」（无 owner 无预算） |
| 覆盖率与**变异/边界测试配套** | 只挂覆盖率阈值（100% 覆盖率可配 0% 变异得分） |
| 可复现构建实测：同 commit 两台机器各构建两次并 diff | 仅靠配置声明可复现（**未 diff 过的一致性只是声明**） |
| 云 runner 之外自建 runner 接板卡 | 假定云 runner 能插 USB |

## 7. 调试与可观测性

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| **一次只改一处**，改完立刻验证 | shotgun debugging（随机改到「好了」） |
| 先找 baseline 再下结论 | 无对照就断言「硬件问题」 |
| 把「加了日志就不复现」判为 **Heisenbug** | 把它当「修好了」 |
| 用 git bisect（仅单调 bug）定位回归 | 对间歇性 bug 用 bisect |
| 实时路径用 **SWO/ITM 或 RTT** | 实时路径用**阻塞式 UART printf**；ISR 内做格式化输出 |
| 环形日志 + 复位原因寄存器 + 驱动静默计数 | 等炸机后才后悔没装黑匣子 |
| 把间歇性故障当**环境问题**查（电源/温度/EMC/焊接） | 只在软件层反复排查 |

## 8. 技术债与文档

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 特征化测试 → 建接缝 → 局部替换 → 灰度 → 一个发布周期后再删旧码 | 大爆炸式重写；在**无测试网**的情况下重构 |
| README / runbook / ADR-Context / why 注释 | 「自文档化代码」绝对化；写没人维护的大文档 |
| 陈旧文档及时更新或删除 | 保留「腐烂」文档（**比没有更糟**，会误导人和 AI agent） |
| 半天为单位的深工作块 + office hours | 认为会议成本只是会议时长 |

## 9. 本土落地（中国大陆场景）

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 把 ASPICE 当**对客户的准入证明**（L2 常为硬门槛） | 为过审而补材料（「为证明评审开过，让项目经理周末召集全员开**补录会议**」） |
| 流程**先问题驱动、后固化** | 一上来就上重型 ALM + 全套规范 |
| 小团队先建「需求确认 / 代码评审 / 版本发布 / 缺陷跟踪」最小规则集 | 「工具崇拜」（配一个月工作流，团队仍在微信群拍板） |
| 留痕：版本号 / 烧录记录 / 配置差异 / 复现条件 / 已排除项 | 在「板未稳、接口未冻」阶段对外承诺交付 |
| 用**数据量化需求价值**换取排期（如「投入 8 人天避免 150 万损失」） | 用「用户需要」这种无法证伪的论据推动排期 |

## 10. 引用纪律（元反模式）

| ✅ 这样做有效 | ❌ 这样做被证伪 / 高风险 |
|---|---|
| 引用时标注来源与可信度等级 | 引用「70% 项目失败」（已被否证） |
| 用 NIST Planning Report 02-3 作为方向性依据 | 引用「IBM 100 倍缺陷成本曲线」（原始研究不可检索） |
| 说明数字的适用边界与年份 | 把供应商/咨询机构自述当作独立统计 |
| 区分「已验证」与「经验性判断」 | 把 ASPICE 咨询商的「缺陷率降 37%」当事实 |
