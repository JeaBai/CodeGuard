# 破坏性测试与混沌工程方法论（Chaos Engineering）

> 定位：project-manager 五阶段框架的 **D4 维度增补包**，将故障注入、混沌实验与韧性验证方法论注入第三/四阶段执行流程。
> 体量标注：🟢 全体量适用 / 🟡 成长型及以上（≥50 人）/ 🔵 大型及跨国（≥500 人）。
> 实证依据：Netflix Chaos Monkey (2011)、AWS Well-Architected Reliability Pillar、Gremlin 2024 State of Chaos Engineering Report、Chaos Mesh CNCF Sandbox。
> 用法：在第三阶段「质量检查」和第四阶段「结果复盘」时，根据体量加载对应词条。

## 一、混沌工程基础概念

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| 稳态假设先行 | 必须先定义系统在正常状态下的可量化行为（稳态），才能判断实验是否偏离 |
| 生产环境优先 | 混沌实验的终极价值在真实生产环境中验证，模拟环境仅作为安全沙箱阶梯 |
| 爆炸半径控制 | 每次实验的影响范围必须可控、可回滚，防止从"演练"变成"事故" |
| 自动化持续 | 混沌实验应集成到 CI/CD 流水线中，成为常态化韧性门禁 |

### 1.2 混沌工程成熟度模型

| 级别 | 特征 | 关键实践 |
|:----:|------|----------|
| L1 手动 | 手动执行基础设施关闭，非系统化 | 偶尔做一次单机故障演练 |
| L2 半自动 | 使用脚本化故障注入，有实验文档 | 定时跑 Chaos Mesh / Gremlin 基础实验 |
| L3 自动化 | CI 集成，实验自动化触发，自动终止 | 每次发布前自动执行 Game Day |
| L4 持续 | 生产环境持续运行混沌实验，自适应 | 系统自动发现脆弱点并注入针对性故障 |

## 二、故障注入模式分类

### 2.1 基础设施层

| 故障类型 | 注入方式 | 爆炸半径 | 体量 |
|----------|----------|:---:|:---:|
| 节点宕机 | `kubectl delete node` / Chaos Mesh NodeChaos | 单节点 → 整集群 | 🟢 |
| 网络分区 | iptables DROP / Chaos Mesh NetworkChaos | 单 Pod → 整个命名空间 | 🟡 |
| 磁盘故障 | `dd if=/dev/zero` / fio 填满磁盘 / Chaos Mesh IOChaos | 单 Pod | 🟢 |
| CPU/内存压力 | stress-ng / Chaos Mesh StressChaos | 单容器 | 🟢 |
| DNS 失效 | CoreDNS 降级 / 自定义 DNS 故障注入 | 服务间调用 | 🟡 |

### 2.2 应用层

| 故障类型 | 注入方式 | 爆炸半径 | 体量 |
|----------|----------|:---:|:---:|
| 依赖超时 | HTTP 代理延迟注入 (toxiproxy / aws-xray-daemon) | 单服务 | 🟡 |
| 依赖返回异常 | Mock 服务返回 5xx / 畸形响应 / 超大数据包 | 单调用链 | 🟡 |
| 数据库慢查询 | pg_sleep() 注入 / 锁竞争模拟 | 单表 | 🟡 |
| 消息队列积压 | Producer 洪泛 + Consumer 降速 | 单队列 | 🟡 |
| 配置错误注入 | ConfigMap 值篡改 / Feature Flag 错误开关 | 单功能 | 🟢 |

### 2.3 云服务层（🔵 大型/跨国）

| 故障类型 | 注入方式 | 说明 |
|----------|----------|------|
| 可用区故障 | AWS Fault Injection Simulator (FIS) / 多 AZ 切换 | 验证跨 AZ 容灾 |
| 区域故障（Region Outage） | 演练流量切换到备用 Region | 验证跨 Region 多活 |
| 凭证过期 | 临时凭证轮换故障 / IAM Role 吊销 | 验证凭证自动刷新 |
| 事件驱动故障 | Lambda/CloudFunction 冷启动超时 | 验证异步补偿机制 |

## 三、D4 破坏性测试检查词条

### 3.1 第三阶段：执行中 — 质量检查

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|:---:|
| CE1 | 系统是否有明确定义的韧性 SLO（如 99.9% 可用性/MTTR<5min）？是否量化了稳态假设？ | 混沌实验的前提：知道"正常"长什么样 | 🟢 |
| CE2 | 最近的故障注入实验中发现了多少未预期的失效？修复率如何？ | 度量混沌实验的实际产出价值 | 🟢 |
| CE3 | 每次发布前是否至少执行一次 Game Day（计划内故障演练）？覆盖了哪些故障场景？ | 建立发布前的韧性门禁 | 🟡 |
| CE4 | 爆炸半径控制策略是否有效？上次实验中是否有故障逃逸出预设范围？ | 防止 Chaos → Accident | 🟡 |
| CE5 | 服务的关键依赖（DB/缓存/消息队列/第三方 API）是否都覆盖了降级方案和故障注入测试？ | 确保依赖链韧性 | 🟡 |
| CE6 | 自动回滚/自动扩缩容机制是否在混沌实验压力下按预期触发？ | 验证自愈系统 | 🟡 |
| CE7 | 混沌实验是否集成到 CI 流水线（如 Argo Workflows + Chaos Mesh）？是否设置了自动终止熔断？ | 混沌工程左移 | 🔵 |
| CE8 | 多 AZ/Region 容灾切换在最近一个季度是否至少演练过一次？RTO/RPO 是否达标？ | 验证跨地域韧性 | 🔵 |
| CE9 | 是否建立了混沌实验数据库（实验历史/影响分析/改进跟踪）？实验频率和覆盖趋势如何？ | 混沌工程可持续治理 | 🔵 |

### 3.2 第四阶段：交付后复盘

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|:---:|
| CE10 | 本阶段混沌实验发现的最严重的弱点是什么？是否已排入下个迭代的修复计划？ | 将韧性发现转化为技术债务项 | 🟢 |
| CE11 | 故障注入覆盖的故障模式比例是多少？还有哪些已知故障模式未覆盖？ | 覆盖度复盘 | 🟡 |
| CE12 | 团队中具备混沌工程设计能力的成员有多少？是否需要外部培训或安全沙箱环境建设？ | 能力建设规划 | 🟡 |

## 四、金丝雀发布与渐进式交付

金丝雀发布（Canary Release）是降低破坏性变更影响的关键手段：

| 阶段 | 流量比例 | 监控时长 | 自动回滚条件 |
|:----:|:--------:|:------:|--------------|
| Canary v1 | 5% | ≥ 30 min | 错误率 > 基线 2× / p99 延迟 > 基线 1.5× |
| Canary v2 | 25% | ≥ 60 min | 同上 + 业务指标异常 |
| Stable | 50% → 100% | 阶梯式 | 任何异常自动中止 |

## 五、使用建议

- **🟢 初创/个人项目**：CE1/CE2 两条核心词条，配合 toxiproxy 做基础依赖超时测试，每周 10 分钟。
- **🟡 成长型**：CE1-CE6 + CE10 纳入第三阶段周检，引入 Chaos Mesh/LitmusChaos 做 K8s 级别的自动化实验。
- **🔵 大型/跨国**：全部词条纳入质量门禁与发布审批流程；建立混沌实验数据库并定期产出韧性态势报告。
