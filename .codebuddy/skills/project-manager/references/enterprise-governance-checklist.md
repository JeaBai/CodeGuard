# 企业级治理检查清单（Enterprise Governance Checklist）

> 定位：project-manager 五阶段框架的**企业级增补包**，将第三轮治理调研（D9-D12）与测试角色重塑（D3）的执行词条注入既有流程。纯新增文件，不改动既有清单。
> 体量标注：🟢 全体量适用 / 🟡 成长型及以上（≥50 人）/ 🔵 大型及跨国（≥500 人）。
> 用法：在第三/四阶段检视时，将对应体量的词条并入 `references/checklist.md` 的执行序列。

## 一、D9 需求与业务价值对齐（挂接第三阶段：执行中）

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|------|
| G1 | 本 Sprint 每个 PR 是否都关联了需求 ID（Jira/Issue Key）？关联率多少？ | 建立需求→代码追溯链，消灭"无源变更" | 🟢 |
| G2 | 需求偏差率（RVI）本季度趋势如何？变动是否集中在同一业务域？ | 量化需求稳定性，识别上游沟通失效点 | 🟡 |
| G3 | 验收标准（AC）是否在开发前以 Gherkin/可测试形式固化？是否存在"开发完再补 AC"？ | 防止 AI 按模糊需求自由发挥导致返工 | 🟡 |
| G4 | 上线功能与原始需求的一致性由谁验收？有无自动化一致性校验（Attest 类）？ | 关闭"需求-实现"最后缺口 | 🔵 |
| G5 | 用户故事映射（Story Map）是否随版本演进更新？ backlog 中是否存在 3 个 Sprint 未动的"僵尸需求"？ | 保持需求资产活性 | 🟡 |

## 二、D10 数据库迁移与数据一致性（挂接第三阶段：质量检查）

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|------|
| G6 | 本次发布涉及的每个迁移脚本，downgrade 是否非空且经过回滚演练？ | 确保"后悔药"真实有效（CI 已由 db-migration-guard 拦截空 downgrade） | 🟢 |
| G7 | 迁移脚本中是否存在 DELETE/UPDATE 无 WHERE、TRUNCATE、DROP 无 IF EXISTS？ | 阻断 AI 生成迁移的致命模式（可启用 CodeGuard AI 专项规则包） | 🟢 |
| G8 | 大表变更（>100 万行）是否有分批/在线 DDL 方案（pt-osc/gh-ost/影子表）？ | 避免锁表导致线上不可用 | 🟡 |
| G9 | 涉及数据回填的迁移，是否有对账校验（行数/抽样哈希/影子表比对）？ | 验证迁移后数据一致性 | 🟡 |
| G10 | 跨服务数据一致性是否依赖 Dual-Write？是否已评估 Outbox 模式改造？ | 消除分布式写入不一致 | 🔵 |

## 三、D11 云成本治理 FinOps（挂接第三阶段：每周检视）

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|------|
| G11 | 本周云支出环比/同比变化多少？是否有异常尖峰及归因？ | 成本异常早发现（初创用云厂商原生预算告警即可） | 🟢 |
| G12 | 新增 K8s 工作负载是否全部声明 requests/limits？单 Pod 配额是否超基线（CPU≤2C/内存≤4Gi）？ | 防止 AI 生成配置超配（CNCF：超支主因为过度配置，已验证） | 🟡 |
| G13 | 容器镜像大小是否超阈值（如 500MB）？是否启用多阶段构建/镜像瘦身？ | 镜像体积直接决定拉取速度与存储成本 | 🟡 |
| G14 | 成本责任是否分摊到团队/服务级（标签/showback）？闲置资源（Datadog：83% 容器成本空闲，已验证）是否定期回收？ | 建立成本责任制 | 🟡 |
| G15 | 是否建立成本基线并在 PR 中自动评论成本影响？FinOps 成熟度处于 Crawl/Walk/Run 哪级？ | 成本左移 + 组织成熟度进阶 | 🔵 |

## 四、D12 变更传播与发布通知（挂接第四阶段：交付后 + 发布时）

| # | 提问词条 | 调研目的 | 体量 |
|---|----------|----------|------|
| G16 | 本次发布是否通过 release-please/CHANGELOG 自动生成发布说明？人工润色耗时多少？ | 发布说明零成本产出 | 🟢 |
| G17 | OpenAPI/接口契约是否有破坏性变更（oasdiff breaking）？是否已 @ 全部下游团队确认？ | 防止 GitHub API 静默变更/Terrateam 类事故（已验证案例） | 🟡 |
| G18 | 回滚/灰度事件是否自动通告干系人（Flagger webhook/钉钉/Slack）？客服与运营是否同步获知？ | 消除"上线后 PM/客服才知道变更"的治理断层 | 🟡 |
| G19 | 发布说明是否区分技术版（工程师）与业务版（LLM 转换的客户价值描述）？ | 让非技术干系人理解变更影响 | 🟡 |
| G20 | 依赖我方 API 的外部客户/合作伙伴是否有变更通告 SLA（提前 N 天 + 迁移指南）？ | 管理下游生态（tianpan.co 10,000 学区事故教训） | 🔵 |

## 五、D3 测试岗位角色重塑（挂接第三/四阶段，🟡 成长型及以上）

| # | 提问词条 | 调研目的 |
|---|----------|----------|
| G21 | SDET 本周工作中，写脚本 vs 设计验收标准 vs 审核 AI 生成用例的时间占比如何？ | 追踪角色从"脚本工人"向"质量编排者"转移进度 |
| G22 | AI 生成的测试用例是否全部经过人工评审？评审发现了哪些 AI 幻觉用例（不存在的 API/错误断言）？ | 控制 AI 用例质量（Sonar：96% 不完全信任，已验证） |
| G23 | 探索性测试范围是否由人定义？AI 自动化覆盖了哪些、刻意留给人做的有哪些？ | 明确人机边界（AI 系统性低估人类认知负荷，ACM CSAI 2025） |
| G24 | 测试团队技能矩阵中，Gherkin 编写/契约测试/混沌工程各有几人达标？下季度培养计划是什么？ | SDET 转型能力盘点 |

## 六、使用建议

- **初创（🟢 词条即可）**：G1/G6/G7/G11/G16 五条零成本词条，每周 15 分钟即可完成检视。
- **成长型**：并入第三阶段每周检视，与既有 55 词条混编执行。
- **大型/跨国**：全部词条纳入质量门禁会议纪要；G15/G20 另需平台与组织配套（见基座报告 v2.0 第 07 章体量矩阵）。
