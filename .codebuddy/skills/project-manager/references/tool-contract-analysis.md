## 一、PMBOK 三域「无法调用」的真实成因

### 1.1 题库是完整的

| 阶段 | 名称 | 题数 | 题号 |
|---|---|---:|---|
| phase1 | 项目可行性研判 | 11 | 1–11 |
| phase2 | 项目启动规划 | 12 | 12–23 |
| phase3 | 项目执行跟踪 | 14 | 24–37 |
| phase4 | 项目复盘沉淀 | 9 | 38–46 |
| phase5 | 持续视野跟踪 | 9 | 47–55 |
| **phase6** | **团队健康（PMBOK Team）** | **8** | **56–63** |
| **phase7** | **干系人（PMBOK Stakeholder）** | **6** | **64–69** |
| **phase8** | **沟通（PMBOK Communications）** | **5** | **70–74** |
| phase9 | 经验资产库 | 6 | 75–80 |
| phase10 | 多 Agent 角色矩阵 | 6 | 81–86 |
| | **合计** | **86** | **1–86（无缺口）** |

### 1.2 真正的成因：**契约泄漏实现细节 + 契约未声明 + 无校验**

```
题库 PHASE_QUESTIONS（内部数据结构，键 = 题号 '56'…'86'）
        │  题号是**内部实现的 key**
        ▼
工具实现：data.get('58')            ← 直接把内部 key 当成对外 API 的入参键名
        ▼
tool schema：answers = "JSON格式的团队评估数据"   ← 契约层**完全不声明**键名
        ▼
调用方（AI/人）：**无从得知该传 {"58": ...}** ⇒ 静默失效
```

**四条成因，缺一不可**：

1. **契约泄漏实现细节**：题号是题库数据结构的 key，被**直接暴露为对外入参键名**
   —— 违反《模块化与接口设计手册》§1.2「依赖抽象，不依赖具体实现」
2. **契约层未声明**：`mcp_usage.md` 只文档化了前 8 个工具（题 1–11 举了例），
   **phase6/7/8 三个工具的键名在 schema、references、SKILL.md 里全无踪影**
3. **无校验 + 静默容错**：`_safe_parse_json(answers, {})` 解析失败就回退 `{}`，
   配合 `data.get(k, '未检测')` 的默认值 → **键名错了也"成功返回"**，只是内容全是占位符
4. **可验证证据**：实测三个工具传空 `{}` → **不报错**，输出全是"未检测/未评估/N/A"

### 1.3 顺带查出的**漏题**缺陷

| 工具 | 题库范围 | 实现使用 | 缺陷 |
|---|---|---|---|
| `team_health_check` | 56–63（8 题） | 58–63 | **漏题 56**（团队人数/角色）、**57**（关键岗位缺口 / Bus Factor） |
| `stakeholder_analysis` | 64–69（6 题） | 64, 66–69 | **漏题 65** |
| `communications_plan` | 70–74（5 题） | 70–74 | ✅ 完整 |

**性质**：漏题**不会报错**，只会让报告**静默缺少该维度**（如团队人数、Bus Factor 缺失）。
这比"调用失败"更隐蔽。

## 二、PMBOK 三域问题的解决思路

### 方案 A（已实施，最小改动）题号 → 语义键 + schema 显式声明

- 16 处 `data.get('58')` → `data.get('skill_gaps')` 等语义键
- schema 里显式列出字段名（保形：仍是 `answers: string`，与既有约定一致）
- ✅ 已落地并实测通过
- **局限**：语义键与题库**脱钩**，映射需人工维护；题库改版不会自动提醒

### 方案 B（推荐，根治）把"问题清单"纳入契约 —— 自描述问答协议

让工具支持 **`answers` 为空时返回该阶段的问题清单**：

```json
{
  "phase": "phase6_team_health",
  "questions": [
    {"key": "skill_gaps", "id": 57, "question": "是否存在关键岗位人力缺口？", "purpose": "Bus Factor 审计"},
    ...
  ]
}
```

调用方流程变为：**先取清单 → 按 `key` 填答 → 再调用**。

**收益**：
- 契约**自描述**，不再依赖外部文档同步
- 题号回归**内部实现**，对外只暴露语义 key + 问题文本
- **漏题当场暴露**（清单里有、实现读不到 → 一眼可见）
- 题库改版只需改题库，契约自动跟随

### 方案 C（防回归，配套必做）契约一致性测试

| 断言 | 防什么 |
|---|---|
| 工具读取的每个 key ∈ 该阶段题库的 key 集合 | 防漏题、防漂移 |
| schema 声明的字段 == 实现读取的 key | 防"文档与代码不一致"（手册 §6 契约测试） |
| 传空 `answers` 时应返回问题清单而非占位文本 | 防静默失效复发 |

> 方案 B + C 组合：B 让契约自描述，C 让契约不漂移。**两者都属"文档驱动的调用保障"。**

## 三、TencentDB 记忆层：**注册表机制不产生实际价值**

### 3.1 现状架构（实测）

```
TencentDB Agent Memory  ~/.openclaw/state/memory-tdai/
    conversations/ . records/ . scene_blocks/
              │
              │  import_from_tencentdb（手动触发，一次性导入）
              ▼
本地副本：<skill>/.codebuddy/experience/
    index.json  +  assets.db(SQLite/FTS5)  +  <asset_id>.json
              │
              │  search() —— 纯本地检索（不读 TencentDB）
              ▼
    load_to_context(asset_id) —— 单资产还原
```

### 3.2 关键实测结论

| 检查项 | 结果 |
|---|---|
| `search()` 是否读 TencentDB | ❌ **纯本地**（keywords/type/tag/project/status + 可选 FTS5） |
| TencentDB 目录何时被读 | **仅** `import_from_tencentdb` 导入那一刻（`memory-tdai` 在代码中仅 3 处出现） |
| 本地副本存储位置 | `<skill>/.codebuddy/experience/` —— **在技能目录内** |
| 导入后是否自动同步 | ❌ 无同步机制，只靠再次手动导入 |

### 3.3 判断：**「统一登记」这层注册表不产生价值，反而净负**

| 维度 | 分析 |
|---|---|
| **token 效果** | **不产生收益。** 把记忆复制到本地**不减少任何 token**。真正降 token 的是「**检索后只注入相关的少数几条**」——那是 **retrieval**，且 TencentDB 本职就提供 |
| **数据一致性** | ❌ **双写**。TencentDB 是**跨团队复用的活记忆**，会持续更新；本地副本**不会自动同步** → 检索到的是**过期快照**，恰好破坏"跨团队复用"的目的 |
| **数据安全** | ❌ **存储位置错误**。落在**技能目录内**，升版本 / 重新部署 / 覆盖安装会**整体替换** → **记忆静默丢失** |
| **元数据重复** | ❌ `visibility / tags / project / version` 这些"复用所需元数据"**本就是 TencentDB 的职责**，在本地再维护一份 = **双重维护**且必然漂移 |
| **职责边界** | ❌ 注册表把 skill 变成了"第二个记忆真相源"，与 TencentDB 争夺权威性 |

> **结论（与用户判断一致）**：**不应引入注册表机制。**
> 它不降 token，却引入双写不一致、版本覆盖丢数据、元数据双重维护三重风险。

### 3.4 推荐做法：**直读 + 薄适配，不落盘**

```
TencentDB（唯一真相源，持续更新）
        │  检索时**直读**（或其查询接口）
        ▼
薄适配层：类型映射（4 类记忆 → 统一检索口径）
        │
        ▼
按需注入：只把**本次任务相关的少数几条**放进上下文   ← 这才是降 token 的来源
```

**要点**：
- **不持久化副本**：检索与加载时直读 TencentDB，保证永远是最新
- **只保留进程内临时索引**（可选，用于加速；**不落盘、不跨会话**）→ 避免双写
- **元数据交由 TencentDB 维护**，skill 侧不另立一套
- `import_from_tencentdb` 的定位需重新评估：若 TencentDB 是长期真相源 → 导入属**冗余复制**；
  仅当存在「TencentDB 数据会被清理、需保全归档」的实际场景时，才作为**归档导出**能力保留
  （且应导到**项目目录**，不是技能目录）

### 职责边界定论（写入代码文档串）

`experience_store` 只是**检索 / 注入的缓存层**，**不是记忆的真相源**；真相源是 **TencentDB**。
因此：**不设本地"注册表"作为第二权威**，不追求双向同步，检索以保证读到最新为准。
