# Architecture Rules Reference

> 本文件定义 CodeGuard Skill 使用的通用架构约束规则。团队使用时，可编辑此文件注入组织级规范。
> 数据基础：基于 GitClear 2025（2.11亿行）、Sonar 2026、DORA 2024、arXiv 2603.28592 等独立验证的实证研究。

## 一、SOLID 原则检查规则

### 1.1 单一职责原则 (SRP)
- **规则**：一个类/模块只应有一个引起变化的原因
- **检测信号**：
  - 类方法数 > 15 → 警告
  - 类代码行数 > 300 → 警告
  - 类代码行数 > 500 → 阻塞
  - 类中存在超过 3 种不同类型的操作（CRUD + 验证 + 格式转换 + 外部调用） → 标记
- **数据支撑**：Sonar 2025 研究发现 >90% AI 代码问题属于代码异味，其中职责过载是最常见类型

### 1.2 开闭原则 (OCP)
- **规则**：对扩展开放，对修改关闭
- **检测信号**：
  - 使用 `instanceof` / `is` 类型判断超过 3 处 → 警告（应使用多态替代）
  - switch-case 在 3+ 不同文件中出现同类判断 → 标记
- **数据支撑**：GitClear 报告显示 AI 代码重构占比从 24% 降至不足 10%，说明抽象层缺失普遍

### 1.3 里氏替换原则 (LSP)
- **规则**：子类必须能完全替代父类
- **检测信号**：
  - 子类重写方法时抛出 `NotImplementedException` → 阻塞
  - 子类方法签名与父类不一致（改变参数类型/返回值） → 警告

### 1.4 接口隔离原则 (ISP)
- **规则**：不应强迫客户端依赖不使用的方法
- **检测信号**：
  - 接口方法数 > 10 → 警告
  - 接口存在 2+ 个不同职责的语义分组 → 建议拆分

### 1.5 依赖倒置原则 (DIP)
- **规则**：高层模块不应依赖低层模块，二者都应依赖抽象
- **检测信号**：
  - 领域层/业务层直接 import 基础设施层（数据库驱动、HTTP 客户端） → 阻塞
  - 使用 `new` 直接实例化外部依赖而非依赖注入 → 警告
- **数据支撑**：arXiv 2603.28592 发现 AI 引入的技术债务中 89.3% 为代码异味，架构分层违规是最常见的异味类型之一

## 二、分层架构约束

### 2.1 通用三层架构规则

```
┌─────────────────────────────────┐
│  Presentation / Controller      │ ← 可依赖: Application, Domain
├─────────────────────────────────┤
│  Application / Service          │ ← 可依赖: Domain
├─────────────────────────────────┤
│  Domain / Core                  │ ← 不可依赖上层
├─────────────────────────────────┤
│  Infrastructure                 │ ← 实现 Domain 接口
└─────────────────────────────────┘
```

### 2.2 依赖方向检测
- **禁止**：Domain 层 import Infrastructure 层 → **阻塞**
- **禁止**：Domain 层 import Presentation 层 → **阻塞**
- **警告**：Application 层直接使用 Infrastructure 具体实现 → 应通过接口
- **警告**：跨层循环依赖 → 标记并建议重构

### 2.3 包/模块依赖检测
- 检测 `import` / `require` / `using` 语句中的依赖关系
- 构建依赖图，检测循环依赖
- 当新增循环依赖时 → **阻塞**

## 三、DRY 原则与重复代码检测

### 3.1 重复代码阈值
- 连续 6 行以上完全相同 → 警告（建议提取）
- 连续 10 行以上完全相同 → 阻塞（必须提取）
- 跨文件相同代码块 > 20 行 → 阻塞
- **数据支撑**：GitClear 发现 AI-heavy 项目复制粘贴代码增长 48%，重复代码块约 10 倍增长

### 3.2 语义重复检测（高级）
- 两个函数签名不同但逻辑结构相同（仅变量名不同） → 警告
- 多个文件中出现相同 if-else 分支结构 → 警告

## 四、命名规范

### 4.1 通用命名约定
- 类名：PascalCase（名词或名词短语）
- 方法名：camelCase（动词或动词短语）
- 常量：UPPER_SNAKE_CASE
- 接口：I 前缀 + PascalCase
- 布尔变量：is/has/can/should 前缀

### 4.2 命名一致性
- 同一概念在不同文件中使用不同名称 → 警告
- 例如：`getUserById` / `fetchUserById` / `retrieveUserById` / `findUserById` 混用 → 建议统一

## 五、函数/方法复杂度

### 5.1 圈复杂度 (Cyclomatic Complexity)
- CC > 10 → 警告
- CC > 15 → 阻塞（需资深审查）
- CC > 20 → 阻塞（必须重构）
- **数据支撑**：CodeRabbit 2025 分析发现 AI 代码产生逻辑错误比人工多 75%

### 5.2 参数数量
- 方法参数 > 5 → 警告（考虑封装为参数对象）
- 方法参数 > 8 → 阻塞

### 5.3 嵌套深度
- 嵌套层级 > 4 → 警告
- 嵌套层级 > 6 → 阻塞

## 六、常见 AI 代码反模式

基于研究报告识别的六大 AI 代码问题：

### 6.1 局部连贯、全局不一致
- **表现**：单个函数逻辑正确，但同一概念在代码库中以多种方式实现
- **检测**：跨文件模式对比，同名概念的不同实现方式
- **频率**：这是 AI 代码最普遍的问题（源于自回归生成的本质缺陷）

### 6.2 能跑就行模式
- **表现**：代码通过编译和测试，但缺乏错误处理、边界检查、日志
- **检测**：
  - try-catch 块为空或仅 `print(e)` → 警告
  - 外部 API 调用无超时设置 → 警告
  - 文件/数据库操作无资源释放 → 阻塞
  - 硬编码密钥/密码 → **阻塞**（安全红线）
- **数据支撑**：Veracode 2025 报告显示 45% AI 代码未通过安全测试

### 6.3 规格遗忘
- **表现**：Prompt 中定义的规范在生成长代码时被遗忘
- **根因**："Lost in the Middle"效应——上下文中间部分准确率骤降至 50% 以下
- **对策**：将架构规则放在每次 Prompt 的最前和最后（首因+近因效应）

### 6.4 无重构生成
- **表现**：AI 只添加新代码，不修改或删除旧代码
- **数据支撑**：GitClear 显示重构占比从 24% 骤降至不足 10%
- **检测**：新增代码与原有功能存在重叠 → 警告

### 6.5 知识负债
- **表现**：代码存在但开发者不理解其设计意图
- **数据支撑**：76% 开发者承认生成了自己不完全理解的代码
- **对策**：关键代码必须附加注释说明设计决策

### 6.6 信任-采纳悖论
- **表现**：开发者不信任 AI（29% 信任度）但不得不使用（84% 采纳率）
- **后果**：审查疲劳，22.7% 的 AI 引入问题逃逸到生产环境
- **对策**：自动化第一层审查，让人专注于高价值判断

## 七、安全红线（不可协商）

以下规则一旦触发 → **直接阻塞**：

1. 硬编码的密码、API Key、Token → 阻塞
2. SQL 拼接（未使用参数化查询） → 阻塞
3. 命令注入风险（`eval`/`exec`/`os.system` 接受外部输入） → 阻塞
4. 无认证的敏感数据端点 → 阻塞
5. 明文日志记录密码/Token → 阻塞
- **数据支撑**：CodeRabbit 2025 发现 AI 代码安全漏洞高出人工 274%

## 八、AI 代码特定度量指标

基于 DORA 2024 和 GitClear 研究，建议追踪以下指标：

| 指标 | 健康值 | 警示值 | 说明 |
|------|--------|--------|------|
| 代码耐久性 | > 80% | < 60% | 14天后未大幅修改的代码占比 |
| AI 代码变动率 | < 20% | > 30% | 14天内被修改或删除的 AI 代码百分比 |
| 重构占比 | > 15% | < 5% | 修改/移动/删除操作占所有变更的比例 |
| 重复代码率 | < 5% | > 10% | 新代码中的重复块占比 |
| CRAP 指数 | < 15 | > 30 | CC² × (1−coverage)³ + CC |
